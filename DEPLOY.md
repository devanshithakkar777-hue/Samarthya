# Deploying the Samarthya pilot: Render + Neon

This is the pilot setup: two Render web services (web, API) and one Neon Postgres database. Nothing in this repo creates
accounts or resources. You do each step below with your own Render, Neon and GitHub accounts.

```
Visitors -> samarthya-web (Next.js, Render) -> samarthya-api (FastAPI, Render) -> Neon Postgres (free)
```

Browsers only ever talk to the web service. It forwards `/api/proxy/v1/...` calls to the API, so database credentials and the
JWT secret live only on the API service.

## Limits to know before launch (verify them again on the day)

These come from the providers' public pages when this was written. Providers change them, so check before you rely on them:
render.com/pricing and neon.com/pricing.

- **Render free web services sleep after about 15 minutes without traffic** and take roughly a minute to wake. The first visitor after a quiet spell waits.
  Free instances have a monthly hour allowance per workspace. Running two always-awake services can use it up, so check the dashboard.
- **Neon Free scales compute to zero after about 5 minutes idle.** The first query after that is slower while it wakes. The free plan has a 1 GB storage limit per project and a monthly compute-hour allowance.
- A visitor after a quiet spell can meet both delays at once. This is acceptable for a pilot with testers, and not for a public launch. See "Upgrading".
- The health checks (`/healthz`) do not touch the database, so Render's checks never wake Neon on their own.

## 1. Put the code on GitHub

Create a private repository, push this folder to it. Do not commit a `.env` file (the `.gitignore` excludes it).

## 2. Create the Neon database

1. In Neon, create a project. **Region: choose the one nearest to your Render region (Singapore for both if Neon offers it; if Neon has no Singapore region, pick its closest Asia-Pacific region and keep Render in Singapore).**
2. Open **Connect**. Copy two strings:
   - **Pooled** (the host contains `-pooler`) -> this becomes `DATABASE_URL`.
   - **Direct** (no `-pooler`) -> this becomes `DIRECT_DATABASE_URL`.
3. Keep `sslmode=require` on both. `postgres://` and `postgresql://` forms are both fine; the app converts them to the right driver form.

Why two strings: the app's connections go through Neon's connection pooler, which suits many short connections. Migrations need
session features the pooler does not support, so they use the direct string. The app already turns off prepared statements for this reason.

## 3. Deploy on Render

1. Render dashboard -> **New -> Blueprint** -> pick the GitHub repo. Render reads `render.yaml` and proposes `samarthya-api` and `samarthya-web`.
2. Render asks for every value marked `sync: false`. Type them in; they are stored only in Render:
   - `DATABASE_URL`, `DIRECT_DATABASE_URL`: from Neon (step 2).
   - `SMTP_*`, `MAIL_FROM`: from your email provider. **Sign-in codes are sent by email, so the API will not start in production without `SMTP_HOST`.**
   - `CORS_ORIGINS`, `SITE_URL`, `API_URL`: you do not know these yet. Enter a placeholder, apply, then set the real values in step 4.
   - `JWT_SECRET` is generated by Render. Do not reuse one from anywhere else.
3. Apply. The API runs `alembic upgrade head` on start (using `DIRECT_DATABASE_URL`), then serves. Migrations run once because the pilot is one instance.
   Do not scale the API past one instance without moving migrations to a separate step first.

## 4. Wire the URLs together

After the first deploy both services have `https://<name>.onrender.com` addresses. In the Render dashboard set:

| Service | Variable | Value |
|---|---|---|
| samarthya-api | `CORS_ORIGINS` | the web service's URL (or your custom domain), no trailing slash |
| samarthya-web | `API_URL` | the API service's URL, no trailing slash |
| samarthya-web | `SITE_URL` | the web service's URL (or custom domain) |

Save; both redeploy. (Render's private network is not used, because free instances may not accept private traffic. Verify this if you move to paid plans, then prefer the private address.)

## 5. First admin and the two reviewers

Samarthya's rule is that no one approves their own work, so you need at least two people with the reviewer role plus one editor account that imports drafts.

Planned roles for the pilot:

| Role in Samarthya | Person | Why |
|---|---|---|
| Primary Reviewer (and admin) | Project founder | Vision, educational accuracy, accessibility, user experience, public-welfare fit |
| Independent Reviewer | Faculty mentor | A second pair of eyes who did not write the content |
| Editor | A separate content-editor sign-in | Imports and edits drafts; cannot publish |

Steps:

1. Sign in on the live site with the founder's email once. If `ADMIN_BOOTSTRAP_EMAIL` is set to that address, that sign-in becomes admin. Then **remove `ADMIN_BOOTSTRAP_EMAIL`** from Render.
2. The faculty mentor signs in once with their own email so an account exists. In the admin area (or with `python -m app.cli`), the admin grants them the reviewer role.
3. Keep the faculty mentor's identity out of public pages (the app only shows role titles). Reviewer attribution is kept in the audit log, which is internal.
4. Create a content-editor account the same way. Drafts the editor imported can then be approved by either reviewer.

## 6. Load the content (as drafts)

Free Render instances may not offer a shell. The simplest route is to run the import from your own computer against the **direct** Neon string.
The string is a secret: type it into your terminal session, do not put it in a file you commit.

```
cd apps/api
pip install -e .
export JWT_SECRET=<any 32+ characters; not used by the import>
export DATABASE_URL='<Neon DIRECT string>'
python -m app.cli import sectors ../../content/imports/sectors.csv --as <editor email>
# ...then roles, qualifications, pathways, pathways_tables, enrich (see content/imports/README.md for the order)
```

Everything lands as drafts. Nothing is public until a reviewer approves it.

## Environment variables

See `.env.example` for the full list with comments. The ones specific to this deployment:

| Variable | Service | Meaning |
|---|---|---|
| `DATABASE_URL` | api | Neon pooled string |
| `DIRECT_DATABASE_URL` | api | Neon direct string, migrations only |
| `RUN_MIGRATIONS` | api | `1` runs migrations on start; set `0` to skip |
| `DB_POOL_SIZE`, `DB_POOL_RECYCLE_SECONDS` | api | Connection pool tuning; defaults are fine for the pilot |
| `LOG_LEVEL` | api | `INFO` by default |
| `TRUSTED_PROXY_HOPS` | api | How many proxies to trust for the visitor's address |
| `JOURNAL_KEY` | api | 32+ random characters; encrypts private journals. Render generates it. **Back it up outside Render**; if lost, journal entries are unrecoverable |
| `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_DAILY_LIMIT` | api | Optional AI companion. Off unless the first three are all set. Nothing is provisioned for you; use your own key only after the guardrails are reviewed |
| `API_URL`, `SITE_URL` | web | Where the API and the site live |

## Security notes

- Database credentials exist only on the API service and in Neon. The web service never sees them.
- CORS allows only `CORS_ORIGINS`. Authentication is by sign-in code by email; the session token stays in an httpOnly cookie on the web service.
- Production start-up refuses to run with a short `JWT_SECRET`, without email settings, or with self-review switched on.
- Logs record method, path, status and timing. They do not record query strings, request bodies or email addresses. Do not add them.

## Rate limiting

Sign-in and report endpoints are rate-limited **per API process**, in memory. This is fine for one instance. If you ever run more than one,
move the counters to Redis first.

`TRUSTED_PROXY_HOPS=1` makes the API trust only the last address Render's proxy adds. Because the web service calls the API over its public address,
that address is the web service's, so **all visitors currently share one rate-limit bucket**. That is safe (it cannot be forged) but means one
abusive visitor can briefly block sign-ins for everyone. To get per-visitor limits, check in the API logs which position in `X-Forwarded-For` holds the real
visitor address on your Render setup, then set the hop count to match. This has not been verified on a live Render deployment.

## Backups, recovery and export

- **Export (do this before every content release and on a schedule):** with the Neon direct string,
  `pg_dump "$DIRECT_DATABASE_URL" --format=custom --file samarthya-$(date +%F).dump`. Store the file somewhere private and off Render.
- **Restore into any Postgres:** `pg_restore --no-owner --dbname "<target direct string>" samarthya-YYYY-MM-DD.dump`.
- **Neon's own history:** Neon keeps a short rewind window and supports branches; the length of the window depends on the plan. Check what your plan includes
  (neon.com/docs) and do not rely on it as your only backup.
- **Recovery drill:** once, before launch, restore a dump into a scratch Neon branch or a local Postgres and confirm the site runs against it.
- Content is the valuable part. The draft CSVs in `content/imports/` plus the audit log in the database are the second copy of it.

## Upgrading, or moving away from Neon

The application only needs a PostgreSQL connection string, so neither move changes code.

- **Paid Neon plan:** upgrade in Neon's dashboard. The connection strings stay the same. This removes the storage cap and lets you control scale-to-zero.
- **Always-on Render:** change `plan: free` to a paid plan in `render.yaml` for the API (and the web service). Removes the sleep delay.
- **Another PostgreSQL provider** (Render Postgres, Supabase, AWS RDS, your own server):
  1. Take a dump (above) and restore it into the new database.
  2. Set `DATABASE_URL` to the new string. If the provider has no pooler/direct split, leave `DIRECT_DATABASE_URL` empty.
  3. Redeploy and check `/readyz`.

## After deploying: checklist

- `https://<api>/healthz` returns ok and `https://<api>/readyz` reports the database reachable.
- The site loads, `/pathways` shows no items yet (drafts are hidden), and sign-in emails arrive.
- A reviewer can publish a test item and a different reviewer cannot be the same person as its editor.
- Export a dump and restore it once.
- Mentors: a mentor profile is only listed after a reviewer who is not that mentor approves it (Admin > Moderation).
- Institutions: create one in Admin > Institutions; the join code is shown once. Staff see aggregates only, and only when at least 10 consenting students exist.
- Crisis numbers on `/live/wellness` are hard-coded with sources and a checked-on date. A reviewer must re-check them against the official sites before launch and on a schedule.
- Web build needs no running API (pages that read it render on demand).
